# Handoff to Part 2 (Legal Analysis)

This document is written for the developer building Part 2. You should be able to work from this file,
`docs/CASE_STATE_SCHEMA.md`, and the example JSON files **without reading any conversation code**.

## 1. What Part 1 does (one paragraph)

Part 1 talks to the complainant, extracts *facts* from their words, asks follow-up questions until the
important facts are present, detects and resolves contradictions with the user, shows a summary, and
records the user's confirmation. Its output is one JSON document: a `CaseState`.

```
Conversation  ──►  Part 1  ──►  CaseState (JSON)  ──►  Part 2  ──►  Legal analysis  ──►  FIR draft
```

## 2. What Part 2 receives

A `CaseState` with `schema_version = "1.0"`, obtained in one of two ways:

```python
# a) over HTTP while the backend runs
import httpx
state_json = httpx.get(f"http://localhost:8000/cases/{case_id}/state").json()["case_state"]

# b) from a file (e.g. the examples below, or one downloaded from the UI)
from app.models.case_state import CaseState
state = CaseState.from_json(open("data/sample_cases/examples/assault_theft_station.json").read())
```

Both give you the same structure. Use the Pydantic class if Part 2 is Python (typed access, `.label()`
helpers); use the raw JSON otherwise.

### Guarantees when `status == "complete"`

- `user_confirmed` is `true` and the user saw `final_summary`.
- No contradiction has `resolved == false`.
- Every fact has a provenance `status`; nothing was invented. `null` + `not_provided` means *not
  mentioned*; `unknown` means the user does not know; `declined` means the user refused.
- Dates are `YYYY-MM-DD`, times `HH:MM`; approximate ones carry `approximate: true` and the user's words
  in `description`.
- `acts[*].type` uses the factual vocabulary below — **these are not offences**.

### What Part 1 deliberately does NOT provide

- No IPC/BNS sections, no offence names, no severity judgement, no "cognizable" flag.
- No assessment of credibility or guilt. Every statement is an allegation by the complainant.
- No fabricated defaults: if `injuries` is empty and `flags.injury_occurred.value` is `null`, the
  question was never answered — do not treat it as "no injury".

## 3. Suggested integration surface

```python
class LegalEngine:
    def analyze(self, case_state: CaseState) -> LegalAnalysis:
        """Part 2: map facts to candidate provisions, retrieve law/case material, draft the FIR."""
```

Inputs you will most likely use:

| Question Part 2 asks | Where to look |
|---|---|
| What allegedly happened? | `acts[]` (`type`, `description`, `by`, `against`), `incident.description`, `timeline[]` |
| Was there violence / a weapon / injury? | `acts[type=physical_assault]`, `weapons[]`, `injuries[]`, `flags.*` (mind `null`) |
| Was property taken or damaged, with force or threat? | `property[]` (`what_happened`, `force_or_threat_used`, `approximate_value`, `recovered`) |
| Threats / harassment pattern? | `acts[type=threat|harassment|stalking_or_following|online_or_message_based]`, `incident.ongoing_or_repeated` |
| Who is accused, are they identified? | `accused[]` (`identity_status`, `name`, `description`, `relationship_to_complainant`) |
| Who is the victim? | `complainant_is_victim`, `victim` |
| When / where? | `incident.date`, `incident.time`, `incident.location`, `incident.location_details` |
| Supporting material | `witnesses[]`, `evidence[]` |
| How solid is each fact? | `Fact.status`, `Fact.approximate`, `contradictions[]` (resolved ones still show what changed) |

Act vocabulary: `physical_assault`, `threat`, `verbal_abuse`, `harassment`, `taking_property`,
`property_damage`, `entering_premises`, `cheating_or_fraud`, `stalking_or_following`,
`online_or_message_based`, `other`.

## 5. What Part 2 should NOT need to know

- how the chat UI works (`frontend/`), how turns are orchestrated (`app/conversation/`),
- the extraction or question prompts, the merge rules, SQLite tables.

If you find yourself needing any of that, the contract is incomplete — open an issue and we will add
the field to `CaseState` rather than have Part 2 reach into Part 1 internals.

## 6. Expected future wiring (not implemented)

```
POST /cases/{id}/confirm  ──►  status=complete
        │
        ▼ (Part 2, later)
POST /cases/{id}/analyze  ──►  LegalEngine.analyze(CaseState) ──► LegalAnalysis JSON
POST /cases/{id}/fir      ──►  FIR draft using CaseState + LegalAnalysis
```

Both endpoints would import `CaseState` from `app.models.case_state` and read state via the existing
`Repository.get_state(case_id)`. Nothing in Part 1 needs to change for that.

## 7. Validation helper

`app/validation/validators.py::validate_case_state(state) -> list[str]` returns structural problems
(bad date format, complete-without-confirmation, open contradictions on a confirmed case). Call it at
the start of `analyze()` and refuse inputs that return a non-empty list.
